# 好好吃饭 · 每日健康菜单（可维护源码版）

从 Figma Make 发布站点 `canvas-energy-75936629.figma.site` 反解重建的可维护工程，并在其上补齐了原项目缺失的功能。

## 界面重构 v2（移动端优先）

- 统一为「灰白纸感 + 森林绿」的克制配色，暖色只保留在少量提示与数据色上
- 手机端改为独立 App 式框架：吸顶品牌栏、4 个底部入口、页内分组切换、悬浮胶囊导航
- 今日页新增深色能量卡（热量环、宏量进度、饮水刻度）与「一句话记一餐」快捷入口
- 周计划、营养分析、报告、食谱、健康记录、设置、登录页全部重排；餐卡改为紧凑图文卡，食谱改为双列瀑布格，报告增加未生成时的引导态
- 弹窗统一为底部抽屉；输入字号 ≥16px，避免 iOS 聚焦缩放；全部页面在 390px 下无横向溢出
- 图片改为本地资源（`public/images/`），不再依赖外链；新增 PWA 图标、离线页面壳与 Service Worker
- 一套代码三端：PWA（Android / iOS / HarmonyOS 通用）+ Capacitor（Android / iOS）+ ArkWeb 壳（HarmonyOS），详见 [`app/MOBILE.md`](app/MOBILE.md)
- **Flutter 版**：`flutter_app/` 使用同一套视觉语言重写，含 5 个一级导航、动画、图表和本地持久化；Android 测试包见根目录 `haohao-chifan-v2.apk`

## 本地运行

```bash
cd app
npm install

# 1) 纯前端开发（AI 建议会走内置文案回退）
npm run dev            # http://localhost:5173

# 2) 带 AI：先起 pi-ai 服务，再起前端（vite 已把 /api 代理到 8787）
cp .env.example .env   # 填网关地址 / 密钥 / 模型
npm run serve          # http://127.0.0.1:8787 同时托管 dist 与 /api/ai/*
npm run dev            # 另开一个终端，前端热更新

# 3) 生产：build 后由 node 服务统一托管
npm run build && npm run serve
```

技术栈：Vite + React 18 + TypeScript + framer-motion 11。样式沿用原站编译后的样式表（`src/styles/app.css`，32KB 手写 BEM 类名），新增功能样式在 `src/styles/extra.css`，因此视觉与原站一致。

## AI 接入（pi-ai）

`server/index.mjs` 用 [`@earendil-works/pi-ai`](https://github.com/earendil-works/pi/tree/main/packages/ai) 把 OpenAI 兼容网关接成三个能力：

| 接口 | 用途 | 输入 |
|---|---|---|
| `POST /api/ai/advice` `kind=tip` | 今日小贴士（JSON） | 目标/已摄入/蛋白质/饮水/已吃/未吃 |
| `…kind=pairing` | 当日三餐搭配建议 | 三餐明细 + 全天合计 + 目标 |
| `…kind=insights` | 本周健康洞察（3 条，JSON） | 日均热量、蛋白质达标天数、饮水、运动、体重变化 |
| `GET /api/ai/schemas` | 三种 kind 的 JSON 契约与返回信封 | — |
| `POST /api/ai/test` | 用最轻的 tip 请求自检 | — |
| `GET /api/ai/status` | 前端探测可用性 | — |
| `GET /api/llm/apis` | 可选协议（OpenAI 兼容 / Responses / Anthropic / Gemini） | — |
| `GET /api/llm/providers` | 提供商列表（含模型、密钥掩码、是否当前） | — |
| `POST /api/llm/providers` | 新增提供商并拉取模型目录 | `{name,baseUrl,api,apiKey?,apiKeyEnv?,defaultModel?}` |
| `PATCH/DELETE /api/llm/providers/:id` | 修改 / 删除提供商 | 同左 |
| `GET /api/llm/providers/:id/models?refresh=1` | 拉取该提供商的模型 | — |
| `POST /api/llm/providers/:id/test` | 设为当前并真发一次请求 | `{model}` |
| `POST /api/llm/active` | 切换当前提供商 + 模型 | `{providerId,model}` |

要点：
- 通过 `createProvider()` + `openAICompletionsApi()` 注册自定义 provider，`envApiKeyAuth()` 从 `PI_GATEWAY_API_KEY` / `WB_GW_API_KEY` 读密钥，`models.complete()` 直连网关。
- 该网关模型会先花 token 思考，思考被 `maxTokens` 截断时正文为空；服务端按 800 → 1800 → 3000 逐级重试，实测 5/5 稳定出文。
- 前端 `lib/ai.ts` 按输入内容哈希缓存 6 小时，首屏直接读缓存（不闪「生成中」）；结构化洞察解析失败会自动重试一次，仍失败才回退内置文案。
- 未配置密钥时接口返回 `available:false`，界面显示「内置」徽标与原因提示，功能不中断。

## 六个 AI 能力

| # | 能力 | 入口 | 输入 → 输出 | 谁算数 | 实测 |
|---|---|---|---|---|---|
| 1 | 一句话记饮食 | 今日菜单页顶部「说一句就记上」 | `"中午吃了碗牛肉面，还喝了杯无糖拿铁"` → 2 条带 kcal/蛋白/碳水/脂肪的条目 | 模型估算营养，**餐次由关键词+时间决定** | 3~5s，3/3 成功 |
| 2 | 一句话记运动/体重 | 健康记录页顶部输入条 | `"下午跑了5公里半小时，晚上称了下56.8公斤"` → 跑步 30min + 体重 56.8 | 模型只抽事实，**卡路里按 MET×体重×时长代码算**（237 千卡） | 3s |
| 3 | 拍照估热量 | 今日菜单页「拍照」 | 餐盘照片 → 食物条目 + 营养 | 模型识别与估算，**总量代码求和** | 13.8s（`cn:deepseek-v4-pro`），识别出杂粮饭/烤红薯/牛油果/番茄丁 |
| 4 | 采购清单 | 每周计划页「生成采购清单」 | 21 道菜 → 按 6 类分组的采购量 | 模型只出**每道菜的食材用量**（缓存），**合并累加、单位纠正、分类全部代码算** | 首次 54s（21 道菜）、命中缓存 0.0s |
| 5 | 口味画像 | 设置页「生成画像」 | 换菜/收藏/删除行为 → 喜欢/排斥/硬约束 | 模型归纳，**推荐时按 dislikes 过滤由代码执行** | 4s |
| 6 | 目标调整建议 | 营养分析页「分析一下」 | 近两周体重、达标率、运动量 → 建议热量目标 | 模型给建议值，**护栏强制 ±200 千卡、1200~3000 由代码截断** | 11s，本次建议「维持 1850」 |

新增端点：

| 端点 | 作用 |
|---|---|
| `POST /api/ai/food` | 一句话 → 食物条目（含合计） |
| `POST /api/ai/exercise` | 一句话 → 运动条目（附代码算出的 kcal）+ 体重 |
| `POST /api/ai/photo` | dataURL 图片 → 食物条目（自动挑当前提供商里第一个非思考型视觉模型） |
| `POST /api/ai/shopping` | 菜名列表 → 分组采购清单（成分按菜缓存到 `.data/dish-ingredients.json`） |
| `POST /api/ai/preference` | 行为记录 → 口味画像 |
| `POST /api/ai/goal` | 周数据 → 目标建议（带护栏） |

全部沿用同一套 JSON 信封与重试阶梯，前端拿到的永远是结构化对象，不做字符串解析。

### 这里的分工是刻意的

模型只负责**把自然语言/图片翻译成结构化事实**，所有数字相加、单位换算、分类、护栏、排序都在 `server/rules.mjs` 里算：

- 卡路里：`MET × 体重 × 时长 × 强度系数`
- 采购量：同菜名出现 N 次就 ×N；同名同单位相加；`鸡蛋 2g` 这种明显错的单位按可数表纠正成 `个`
- 食材名归一：`南瓜（去皮去籽后可食部）` → `南瓜`，避免同类拆成两项
- 目标护栏：单次调整 ≤200 千卡，且限制在 1200~3000
- 餐次：文本关键词（中午/晚上/早上）+ 时间兜底，不信任模型判断

## AI 返回的 JSON 契约

统一信封（HTTP 200，失败也是 200 + `ok:false`，便于统一解析）：

```json
{
  "ok": true,
  "kind": "insights",
  "data": { "score": 58, "items": [{ "title": "饮食趋势", "text": "…", "severity": "watch", "metric": "general" }] },
  "text": "由 data 派生的可读文本（前端兜底/复制用）",
  "meta": { "provider": "pi-gateway", "model": "global:deepseek-v4.1-flash", "ms": 15527, "usage": { "totalTokens": 1024 }, "raw": "模型原始输出（仅调试）" }
}
```

三种 `data` 形状：

| kind | 字段 |
|---|---|
| `tip` | `headline`（≤48 字）、`action`、`reason`、`tone`（praise / nudge / warn） |
| `pairing` | `verdict`（balanced / low_calorie / high_calorie / low_protein）、`summary`、`gaps[]`（`nutrient` / `delta` / `suggestion`） |
| `insights` | `score`（0-100 或 null）、`items[]`（`title` / `text` / `severity`（good / watch / act）/ `metric`） |

调用示例：

```bash
curl -s -X POST http://127.0.0.1:8787/api/ai/advice \
  -H 'content-type: application/json' \
  -d '{"kind":"tip","input":{"goal":1850,"consumed":420,"protein":23,"waterMl":1500,"waterTargetMl":2000,"eaten":["菠菜蘑菇欧姆蛋"],"remaining":["日式鳗鱼杂粮饭","菌菇豆腐汤"]}}' \
  | jq '.data'
```

为了"模型一定吐可解析的 JSON"，服务端做了四件事：

1. system prompt 里给**键名列表 + 带示例值的骨架**，并显式禁止回显输入数据（否则模型会把入参换个键名返回）；
2. 请求带 `response_format: { type: "json_object" }`（OpenAI 兼容网关的标准 JSON 模式）；
3. `extractJson()` 容忍代码块、前后废话、尾随逗号；`validate()` 校验键与类型；`normalize()` 补齐漏键；
4. 失败按 `预算 ×1 → ×2 → ×3` 重试，并把**上一次的具体问题**（"你在回显原始数据"/"字段缺失"）回灌给模型。

另外两处容错是实测踩出来的：模型常把 `items` 写成字符串数组，或把标题并进正文——`coerceItems()` 会按「标题：正文」拆分并推断 severity；文本超长时按标点截断，不会出现半句话。

## 多提供商怎么工作

- `server/llm.mjs` 是注册表：每个提供商对应一个 pi-ai `provider`（`llm_<id>`），按 `api` 字段选实现（`openAICompletionsApi` / `openAIResponsesApi` / `anthropicMessagesApi` / `googleGenerativeAIApi`）。
- 提供商配置持久化在 `app/.data/llm.json`（`0600`）。密钥两种存法：直接写进文件，或只存**环境变量名**（`apiKeyEnv`），运行时读取——环境变量方式下磁盘上没有任何明文密钥。
- 接口返回的密钥一律是掩码（`sk-…abcd`）或「环境变量 XXX」，浏览器拿不到明文；`/api/ai/advice` 只回传文本与 token 用量。
- 首次启动自动用 `PI_GATEWAY_BASE_URL` / `WB_GW_API_KEY`（或 `PI_GATEWAY_API_KEY`）播种一个提供商，之后完全可以在 UI 里增删。
- 切换提供商后前端把选择写进 localStorage，下次打开自动同步给服务端。

## 打不开 / 白屏怎么办

1. **先确认服务在跑**：`cd app && npm run serve`，然后开 http://127.0.0.1:8787/ （`localhost:8787` 也支持，服务同时监听 IPv4/IPv6 回环）。
2. **不要用 `file://` 直接打开 `dist/index.html`**：ES module 跨源限制必然白屏，必须经服务。
3. 页面本身有三层兜底，正常情况下看不到纯白屏：
   - `index.html` 内联脚本：模块加载失败 / 6 秒未挂载 → 显示「页面没能加载完」+ 重新加载 / 清缓存重试
   - `ErrorBoundary`：任意页面运行时崩溃 → 显示错误信息 + 刷新 / 清本地数据后刷新
   - `cache-control`：`index.html` 为 `no-cache`（避免旧 HTML 引用已删除的 JS），`/assets/*` 为 `immutable`
4. 本地存储损坏（旧版本结构、手改过）不再崩：`store` 会逐字段校验并回退默认值。

### 一个非显而易见的坑

图表 `svg { min-width: 520px }` 与 grid 子项默认的 `min-width: auto` 叠加，会把页面撑到 578px；手机浏览器为容纳溢出会**缩小视口**，于是 `position: fixed` 的底部导航被推到可视区之外——表现为"导航点不动、点击穿透到图表"。修法是给 grid 子项加 `min-width: 0`，让滚动发生在图表容器内部。

### 实现

| 层 | 做法 |
|---|---|

| 状态 | 存储位置 | 说明 |
|---|---|---|
| 未登录 | — | 显示登录页，可选「先以游客身份逛逛」 |
| 游客 | 仅 `localStorage` | 顶部有提示条，说明只存本机 |

## AI 日报与周报

导航新增 **报告**（第 7 项），分日报/周报两栏。

**分工和别处一致**：所有数字先在前端按统一口径算好（`src/lib/report.ts`），模型只负责解读和给建议——所以报告里写的"日均 1,443 千卡"和趋势图、KPI 卡永远一致。

| | 日报 | 周报 |
|---|---|---|
| 选择 | 本周任一天（周一到周日切换） | 本周整体 |
| 输入 | 当日热量/蛋白/碳水/脂肪、饮水、运动、体重、完成餐次 | 每日热量序列、日均、蛋白达标天数、日均饮水、运动总量、体重与腰围变化、记录天数 |
| 输出 | `headline` 一句话结论 + `score` 0-100 + `summary` + `highlights[]`（good/watch/act 三档）+ `tomorrow[]` 1-3 条 | 同上 + `trend`（better/steady/worse）+ `wins[]` / `risks[]` + `nextWeek[]` |
| 端点 | `POST /api/ai/daily-report` | `POST /api/ai/weekly-report` |

细节：

- 换日期或换模式会清空上一份结果，避免把周三的结论当成周四的
- 「复制文本」把报告转成可粘贴的纯文本（带数字摘要），优先用异步剪贴板，失败退回 `textarea + execCommand`
- 没有记录的那一天按钮直接置灰，并提示"先去首页标记完成或记一笔"——不给模型喂空数据编结论
- 周报的日均饮水按**有喝水的天数**平均，不把没记录的日子算成 0（否则会误判成"严重缺水"）
- 报告缓存按日期/周存在 `hh.ai.v2.*`，重复点击不会重复计费

## 数据可信度与手感（第一、二梯队）

### 本地食物成分表兜底

模型负责「你吃的是什么」，成分表负责「多少千卡」——两者解耦后同一句话不会再飘：

- `server/foodtable.mjs` 内置 **77 条**常用食物（主食/蛋白/蔬菜/水果/饮品零食），每条含 `per100`（kcal/蛋白/碳水/脂肪）与「一份」的参考克数
- 命中规则：先精确匹配（含同义词），再「包含」匹配，且**覆盖度要 ≥75%**——否则「牛肉面」会被错判成「牛肉」
- 克数推断：文本里的 `150g / 300ml` 直接用；写「2个 / 3片」就按该食物单份克数乘；都没有才用默认份量
- 每一条都返回 `source`（`table` / `model`）与 `sourceLabel`，UI 上显示「成分表」或「模型估算」标签，用户能看出这条数据有多可信
- 复合菜（牛肉面、麻辣香锅）表里没有 → 仍标「模型估算」，不假装精确

调试接口：`GET /api/food/lookup?q=鸡蛋` 返回命中项与整张表大小。

### 对话式修正草稿

识别完了才发现「那碗面我只吃了一半」——不用手改数字，直接说：

- 弹窗草稿下方有输入框 + 4 个快捷词（吃了一半 / 没吃完 / 加了一份小菜 / 其实没喝饮料）
- 走 `POST /api/ai/refine`，携带当前清单 + 你的说明，返回**完整修正后的清单**，再走一遍成分表校准
- 模型会保留没提到的条目，只改涉及的部分，并回一句「改了什么」

### 撤销

所有写操作给 6 秒撤销窗口（toast 上带按钮）：记录饮食/运动/体重/围度、删除各类记录、换菜、复制昨天、常吃快加。

### 份量与常吃

- 草稿每行有 `×½ / ×1 / ×1.5 / ×2` 倍率，**从原始值重算**（不是连乘，避免误差累积）
- 首页「常吃」列出出现次数最多的 3 个食物，点一下直接记；「复制昨天」把前一天的追加餐与完成状态搬到今天，可撤销

### 换菜给候选

「换一个」不再随机：给 3 个带理由的候选——**热量最接近 / 蛋白更高 / 更清淡**，候选会避开口味画像里的排斥项。

### 围度

健康记录页新增围度卡：记录腰围、显示 `76.5 → 75.2 cm` 变化、可删可撤销。默认日期跟随应用内"今天"（2025-09-19），与趋势图一致。

## 趋势图与每日提醒

### 体重 / 热量双轴趋势 + 月视图

- 新增 `intakeByDate`（`YYYY-MM-DD → 千卡`）记录每日实际摄入：首页每次标记完成/记一笔都会写入；没有记录的日子**不写 0**，图上就是空白，避免"这天没吃"的误读
- `TrendChart` 用自己的 SVG 画双轴：柱=每日摄入（左轴，超目标变暖色）、折线=体重（右轴）、虚线=热量目标；只用 `viewBox` 自适应，无图表库依赖
- 营养分析页周期切换：**本周 / 本月 / 三个月**。本周数据用「计划 + 完成情况 + 追加餐」推算，月/季读每日历史
- 图下摘要：`记录 7 / 30 天 · 日均 1,531 千卡 · 体重 58.9 → 56.9 kg`；一条记录都没有时给出引导文案
- KPI 卡与 AI 洞察输入都改用真实日均，不再有写死的月/季假数据

### 每日提醒

- 设置页新增「每日提醒」卡：总开关 + 三个时间（喝水 10:30 / 记得吃饭 12:00 / 称重 07:30），可改时间、可单独试听
- 到点走 `Notification` 系统通知；**没授权或被拒绝时自动退回站内 toast**，「允许通知」按钮会请求权限并回报结果
- 同一提醒同一天只响一次（`reminders.fired[key] = 当天日期`），避免每 20 秒检查时重复弹
- 诚实说明写在卡片里：提醒由页面内定时器驱动，**需要保持本站标签页打开**，关掉不会响

| 今日菜单「添加食物」 | 原来的手动选择弹窗 | toast「已添加「牛肉面」到午餐」 |
| 健康记录「记一笔（一句话）」 | 同一个 `AiLogModal` 的运动/体重模式 | 确认后 `addExercise` / `addWeight` + toast |
| 每周计划「生成采购清单」 | `ShoppingList` 弹窗（整周 / 只今天，可复制） | 复制成功 toast |
| 设置「添加提供商」 | 卡片内联展开表单（预设 + 协议 + 密钥） | toast「已添加提供商」 |

弹窗细节：

- 图片先压缩到长边 1024（`compressImage`）再上传，避免几 MB 的 base64
- 弹窗底部操作条 `position: sticky`，草稿很长时「确认入库」始终可点
- 粘贴/拖拽入口共用同一条处理链，识别失败会回显具体错误

toast 覆盖清单：记录饮食/运动/体重、完成或取消完成、换菜、喝水、收藏食谱、换模型、切提供商、删除提供商、体重/运动记录删除、目标应用、数据导入导出。统一 2.4 秒自动消失，右下角。

## UI 细节

- **下拉框统一样式**：全局 `select` 用 `appearance:none` + 细线 chevron（内联 SVG），并统一右侧留白；此前组件里的 `background:#fafaf6` 简写会把箭头重置成 `none`，现已改成 `background-color`
- **模型下拉改为可搜索**：原生 `<select>` 放 54 个模型没法用，换成自建 combobox（搜索框 + 名称/ID/credits/思考型标记 + 当前项勾选），支持 Esc 与点击外部关闭、回车选第一个匹配
- 餐次、强度这类小枚举仍用原生 select，但共用同一套箭头样式

## 排障：AI 不可用 / 页面是旧版本

启动时会先请求 `/api/ai/status` 自检，不通过就显示一张说明页而不是让功能"神秘失灵"：

- 打开的是 `:4173` 这类静态预览端口 → 提示该端口只有页面没有接口，改用 `127.0.0.1:8787`
- 8787 上服务刚重启/被旧进程占用 → 提示重新 `npm run serve`
- 直连不上 → 提示先启动服务，附「我已经启动了，重试」按钮

> 本次真实踩坑：一个几小时前的 `vite preview`（4173）一直挂着旧构建，打开它既没有新功能、`/api/*` 也全是 404，看起来就像"AI 坏了、数据不同步"。这类端口一律不要当入口。

## 已知限制

- 食谱的食材用量、做法步骤、宏量营养素是按菜品配比补写的内容（`src/data/recipes.ts`），原项目只有菜名/时长/热量/难度；后续建议由营养师校对。
- 每周计划里除周四外的菜品名来自原项目 `w` 数据，营养值同为测算值。
- 图片仍走 Unsplash 外链，离线环境需替换为本地资源。
- AI 建议依赖外部网关：离线或未配置密钥时只显示内置文案；生成内容属于营养建议性质，不构成医疗意见。
- 健康记录与饮食数据目前只存在浏览器 localStorage，换设备不同步。
